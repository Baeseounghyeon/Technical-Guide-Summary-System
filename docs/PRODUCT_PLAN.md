# 벤더 기술 가이드 요약 시스템 — 제품 기획 및 설계

> 작성일: 2026-10-15 · 상태: 초안 (1단계 착수 전)

## 1. 확정된 결정 사항

| 항목 | 결정 |
|---|---|
| 제품 형태 | 웹 서비스 (멀티 테넌트) |
| AI 모델 | 개인 사용 기간: 본인 Claude 구독 (Claude Code CLI 경유). 다른 사람에게 공개할 때: Claude API (`claude-opus-5-5`). 설정 하나로 전환 |
| 입력 형식 | PDF, Word(.docx), PowerPoint(.pptx), 웹 문서 URL |
| 문서 분량 | 한 건당 100~500쪽 → 목차 단위로 나눠 병렬 처리 |
| 기술 스택 | 백엔드 Python(FastAPI), 프론트엔드 React(TypeScript) |
| 피드백 방식 | 목차 항목별 검토 (승인 / 직접 수정 / 코멘트로 재생성), 전 항목 승인 시 최종 문서 생성 가능 |
| 산출물 양식 | 기본 양식 제공 + 파트너 템플릿(.dotx/.potx) 업로드 지원 |
| 도메인 | **벤더 단위**. A 벤더 도메인의 파트너는 B 벤더 도메인을 볼 수 없음. 관리자 승인 시에만 예외 열람 |
| 계정 | 자유 가입 → 관리자가 소속 파트너사와 벤더 도메인을 지정해 승인 |
| 개발 순서 | 단계별 MVP (아래 6절) |

## 2. 용어

- **벤더(Vendor) = 도메인(Domain)**: 기술 가이드 원본을 만든 제조사. 데이터 접근 경계의 기본 단위.
- **파트너사(Partner)**: 벤더 제품을 지원하는 회사. 여러 벤더 도메인에 동시에 속할 수 있음.
- **원본 문서(Source Document)**: 사용자가 가져온 벤더 기술 문서.
- **요약 가이드(Guide)**: 원본 문서를 목차별로 요약하고 번역한 결과물. 버전으로 관리.
- **파트너 가이드**: 파트너사가 자체 제작한 기술 문서 (4번 기능의 비교 대상).

## 3. 사용자와 권한

| 역할 | 권한 |
|---|---|
| 플랫폼 관리자 | 가입 승인, 파트너사 및 벤더 도메인 관리, 타 도메인 열람 승인, 전체 감사 로그 |
| 파트너 관리자 | 자사 엔지니어 관리, 자사 템플릿과 로고 관리, 자사 문서 전체 열람 |
| 엔지니어 | 소속 도메인 안에서 문서 업로드, 요약 검토, 문서 생성, 커뮤니티 참여 |

접근 규칙
- 원본 문서, 요약 가이드, 파트너 가이드는 **같은 벤더 도메인 + 같은 파트너사**에서만 보임 (파트너사 간 공유 없음).
- 커뮤니티는 **같은 벤더 도메인의 모든 파트너사**가 함께 보는 공간.
- 타 도메인 커뮤니티 열람은 `열람 요청 → 플랫폼 관리자 승인(기간 지정)` 절차로만 허용하고, 승인 이력을 남김.

## 4. 시스템 구성

```
[브라우저: React + TypeScript]
        │ REST API
[API 서버: FastAPI] ── [DB: PostgreSQL (개발 중에는 SQLite)]
        │                        ▲
        │ 작업 등록               │ 진행률·결과 저장
        ▼                        │
[작업 처리기(Worker)] ── 문서 파싱 / Claude API 호출 / Word·PPT 생성
        │
[파일 저장소: 로컬 폴더 → 운영 시 S3 호환 스토리지]
```

- 500쪽 문서 요약은 몇 분이 걸리므로 API 서버가 직접 처리하지 않고 **작업(Job) 테이블 + 별도 Worker 프로세스**로 처리한다. 화면은 진행률(예: 37/120 섹션 완료)을 보여준다. 초기에는 Redis 없이 DB 기반 큐로 시작하고, 부하가 커지면 Celery/arq로 바꾼다.
- 주요 라이브러리

| 용도 | 라이브러리 |
|---|---|
| PDF 파싱 | PyMuPDF (책갈피 목차 `get_toc()`, 글꼴 크기 기반 제목 추정) |
| Word / PPT 읽기·생성 | python-docx, python-pptx |
| 웹 문서 추출 | httpx + trafilatura |
| Claude 호출 | anthropic (공식 Python SDK) |
| DB | SQLAlchemy 2 + Alembic |
| 화면 | React, Vite, TanStack Query, TipTap(요약 편집기) |

## 5. 핵심 처리 흐름 (1단계)

### 5.1 문서 가져오기 → 목차 확정
1. 파일 업로드 또는 URL 입력, 벤더 도메인 선택, 목표 언어 선택(예: 한국어).
2. 형식별 파서가 문서를 **공통 목차 트리**로 바꾼다. 각 섹션은 제목, 단계(level), 원본 쪽 범위, 본문, 표, 이미지 위치를 가진다.
   - PDF: 책갈피 목차 → 없으면 글꼴 크기로 제목 추정 → 그래도 불명확하면 문서 앞부분의 "목차" 페이지를 Claude로 해석.
   - Word: 제목 스타일(Heading 1~3). PPT: 구역(Section)과 슬라이드 제목.
   - URL: 같은 경로 아래 문서 페이지를 정해진 개수까지 수집, h1~h3을 목차로 사용.
3. **목차 확인 화면**: 사용자가 추출된 목차를 보고 요약 대상에서 제외할 부분(법적 고지, 색인, 부록 등)을 빼거나 섹션을 합친다. 불필요한 비용과 시간을 줄이는 단계.

### 5.2 요약 + 번역
- 섹션마다 Claude를 한 번씩 호출해 **요약과 번역을 동시에** 처리한다 (동시 실행 수 제한, 실패 시 재시도).
- 너무 긴 섹션은 나눠 요약한 뒤 합치고, 너무 짧은 섹션은 묶어서 처리.
- 요약 규칙(시스템 프롬프트)
  - 명령어, CLI, 설정값, 파일 경로, 포트, 버전 번호, 제품명은 **번역하지 않고 원문 그대로** 둔다.
  - 경고/주의(Warning, Caution) 문구는 빠짐없이 유지한다.
  - 절차는 번호 목록으로, 원본 쪽 번호를 출처로 남긴다.
- **벤더별 용어집**: 같은 벤더 문서끼리 번역 용어를 통일한다. 용어집은 프롬프트 앞부분에 고정해 프롬프트 캐싱으로 비용을 줄인다.
- 결과는 구조화 출력(JSON: 요약 본문, 핵심 절차, 주의사항, 출처 쪽)으로 받아 화면과 문서 생성에 그대로 쓴다.
- 섹션 요약이 끝나면 문서 전체 개요(Executive Summary)를 한 번 더 생성.

### 5.3 피드백 (필수)
- 섹션 상태: `초안 → 검토 중 → 승인` (재생성 중, 수정됨 포함)
- 사용자 동작: 승인 / 편집기로 직접 수정 / 코멘트를 달아 재생성 (예: "설치 전 사전 조건을 더 자세히")
- 모든 수정과 재생성은 섹션별 버전으로 남겨 이전 버전과 비교, 되돌리기를 할 수 있다.
- **모든 섹션이 승인되어야** 최종 문서 생성 버튼이 열린다.

### 5.4 최종 문서 생성 (Word / PowerPoint)
- 템플릿 선택: 기본 양식 또는 파트너사 템플릿.
- 선택 항목 (사용자가 요청할 때만 포함)
  - 파트너사 로고: 표지와 머리글.
  - 이력 관리 표: 문서 버전, 작성일, 소속 회사, 소속 부서, 엔지니어 이름, 연락처, 메일, 변경 내용.
- Word 구성: 표지 → 이력 관리 표 → 목차 → 개요 → 섹션별 요약 → 원본 출처.
- PPT 구성: 표지 → 개요 → 대단원별 1~N장(핵심 절차와 주의사항 위주) → 연락처.
- 생성할 때마다 문서 버전을 올리고, 생성 파일과 당시 이력 정보를 함께 보관한다.

## 6. 단계별 개발 계획

### 1단계 — 요약·번역·문서 생성 (기능 1~3)
- 회원가입과 관리자 승인, 파트너사·벤더 도메인 기본 구조 (3단계 확장을 위해 처음부터 반영)
- 문서 업로드 및 파싱 (PDF, Word, PPT, URL), 목차 확인 화면
- 요약·번역 작업 처리기, 진행률 표시
- 섹션별 검토 화면 (승인, 편집, 코멘트 재생성, 버전 비교)
- Word/PPT 생성, 로고, 이력 관리 표, 파트너 템플릿
- 완료 기준: 300쪽 PDF 한 건을 올려 한국어 요약본을 검토하고 Word와 PPT로 내려받을 수 있다.

### 2단계 — 파트너 가이드 비교와 오류 수정 (기능 4)
- 파트너 가이드 업로드 → 요약 가이드의 섹션과 자동 매칭 (제목 유사도 + Claude 판단).
- 매칭된 쌍마다 오류 후보를 찾는다: 잘못된 값이나 명령어, 빠진 절차, 구버전 내용, 원본과 모순되는 설명.
- **오류 판정 근거는 요약본이 아니라 벤더 원본 문서**로 확인한다 (요약 과정에서 생략된 내용을 오류로 착각하지 않도록).
- 각 오류 후보는 `수정 전 / 수정 후 / 사유 / 근거(원본 쪽 번호) / 심각도`로 보여주고, 사용자가 수락 또는 거절.
- 수락된 수정은 Word **변경 내용 추적** 형태로 반영한 파일을 만들고, 모든 판단을 수정 이력으로 남긴다 (누가, 언제, 수락/거절, 사유).

### 3단계 — 벤더 도메인과 커뮤니티 (기능 5~6)
- 도메인별 커뮤니티: 이슈 처리 경험 게시판(제품, 버전, 증상 태그, 해결 여부), 댓글, 검색.
- 온라인 세션 일정 공유: 일정 등록, 캘린더 보기, 참석 의사 표시.
- 타 도메인 열람 요청 및 승인 화면, 승인 기간 만료 처리, 감사 로그.

## 8. Claude API 사용 방침

- 모델: `claude-opus-5-5` (1M 컨텍스트, 최대 출력 128K).
- 호출 방식: 긴 입력이므로 스트리밍 호출, 적응형 사고(adaptive thinking), 작업 난이도에 맞춰 effort를 명시 (기본 `medium`).
- 안전장치: 응답 거절(`refusal`) 시 서버 측 자동 대체 모델(`fallbacks: "default"`)을 켜 둔다.
- 비용 절감
  - 시스템 프롬프트와 용어집에 프롬프트 캐싱 적용.
  - 급하지 않은 대량 처리는 Batch API(50% 할인)를 선택 옵션으로 제공.
- 비용 추정 (참고용 대략치): 500쪽 ≈ 입력 30만 토큰 + 출력 5만 토큰 → 문서 1건, 언어 1개당 약 2~3달러. 재생성과 2단계 비교는 별도.
- API 키 발급 전에는 `LLM_PROVIDER=mock` 설정으로 가짜 요약을 돌려 화면과 흐름을 먼저 완성한다.

## 9. 보안·운영 고려 사항

- 벤더 문서는 Claude API로 전송된다. 벤더와의 NDA나 재배포 조건에 문제가 없는지 확인 필요.
- 모든 문서와 게시물 조회에 도메인·파트너사 권한 검사를 서버에서 강제하고, 열람 이력을 감사 로그로 남긴다.
- API 키는 `.env`에만 두고 저장소나 채팅에 올리지 않는다.

## 10. 남은 확인 사항 (1단계 진행에 지장 없음)

1. 운영 서버 위치: 사내 서버, AWS, Azure 등 (1단계는 로컬에서 개발).
2. 화면 언어: 한국어만, 또는 다국어 UI 필요 여부.
3. 2단계 비교 대상 파트너 가이드의 형식 (주로 Word인지).
4. 커뮤니티 알림 방식 (메일, 사내 메신저 연동 등).

## 11. 진행 현황 (2026-10-15)

개발 환경: Python 3.12.10, Node.js 24.20.0, Git 2.55.0 설치 완료. 실행 방법은 [README](../README.md) 참고.

1단계 뼈대 완료 항목
- 가입 신청 → 관리자 승인, 파트너사·벤더 도메인 지정, 도메인·파트너사 단위 접근 격리
- PDF(책갈피 목차, 없으면 글꼴 크기 추정)·Word·PPT·웹 URL 파싱, 목차 확인 화면(법적 고지·색인 기본 제외)
- 요약·번역 작업(가짜 요약 엔진으로 동작 확인, Claude 연동 코드 작성), 진행률 표시
- 목차 항목별 승인 / 직접 수정 / 코멘트 재생성, 버전 이력
- Word/PPT 생성: 표지, 문서 이력 표, 목차 필드, 로고, 파트너 템플릿(.dotx/.potx 포함)

1단계에서 남은 작업
- 실제 Claude API로 요약 품질 확인과 프롬프트 조정 (API 키 필요)
- 아주 긴 섹션 분할 요약, 짧은 섹션 묶음 처리
